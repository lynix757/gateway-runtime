# Canonical Audit Event Contract

Version: 1.0
Status: Baseline

## Purpose

Define one canonical server-side audit event contract shared by REBFF, Application APIs, Storage Gateway, Streaming Gateway, WebSocket Gateway, and future gateway runtime roles.

Authoritative audit events are generated by trusted server-side components. Browser/mobile generated data is supplemental telemetry only.

## Canonical shape

```json
{
  "schema_version": "1.0",
  "event_id": "01J...",
  "event_time": "2026-09-22T10:15:21.123Z",
  "source": {"service":"rebff","role":"rebff","instance":"rebff-7d9f5"},
  "actor": {"type":"user","subject":"user-123","tenant_id":"tenant-01"},
  "client": {"type":"browser","app_id":"asset-portal","platform":"web","app_version":null,"device_id":null,"ip":"203.0.113.10"},
  "action": "asset.read",
  "target": {"type":"asset","id":"A001"},
  "outcome": {"result":"allow","reason":"authorized"},
  "request": {"request_id":"req-123","trace_id":"trace-456"},
  "metadata": {"province_id":"50","project_id":"P001"}
}
```

## Rules

- Use one schema for browser, mobile, desktop, service, and gateway traffic.
- Use canonical actions such as `asset.read`, `authorization.allow`, `storage.upload.request`, and `websocket.connect`.
- Do not encode client channel in action names.
- Keep REBFF authorization and Application API business decisions as separate events.
- Correlate related events with the same `request_id` and `trace_id`.
- Always use `client.ip`; do not create channel-specific IP fields.
- Use `metadata` only for event-specific non-secret context.
- Do not record secrets or raw sensitive payloads.
- Start with `schema_version = 1.0`.

## Trust model

```text
Browser -> REBFF -------------------+
                                    |
Mobile -> Application API ----------+
                                    |
Storage Gateway --------------------+
Streaming Gateway ------------------+--> Canonical Audit Contract
WebSocket Gateway ------------------+        |
                                             v
                                      Audit Collector / Sink
                                             |
                                             v
                                      Audit Store / SIEM
```

The server that makes or enforces the security/business decision is the authoritative audit producer.

## Cross-component example

```text
Browser
   |
   v
REBFF
   |  audit: authorization.allow
   v
Application API
   |  audit: asset.read
   v
Domain / Data
```

Mobile uses the same schema. Only `source` and `client` differ.

## Versioning

Backward-compatible additive changes may increment the minor version. Semantic breaking changes increment the major version. Consumers should tolerate unknown additive fields within the same major version.

## Implementation migration

Current `internal/audit.Event` is a simpler internal type.

Migrate in a dedicated change to a shared contract package while preserving the existing `audit.Sink` abstraction.

Suggested package:

```text
internal/auditcontract/
  event.go
  actor.go
  client.go
  target.go
  outcome.go
  validator.go
```

## Service and actor correlation

For service-to-service calls, keep workload identity and human/principal identity separate.

Example:

~~~json
{
  "source": {"service":"storage-runtime","role":"storage","instance":"storage-7d9f5"},
  "actor": {"type":"user","subject":"user-001","tenant_id":"tenant-01"},
  "client": {"type":"service","app_id":"asset-api","platform":"service"},
  "action": "storage.upload.request",
  "target": {"type":"storage_target","id":"asset"},
  "request": {"request_id":"req-123","trace_id":"trace-456"},
  "metadata": {"project_id":"project-22"}
}
~~~

The authenticated workload identity (for example asset-api) must not replace the actor identity (for example user-001). Both are needed to answer who initiated the business action and which trusted service performed the technical call.

Transport headers such as X-Service-Identity and X-Actor-Subject are not identity proof. They are acceptable only after a trusted component derives and overwrites them from validated user/workload identity.
